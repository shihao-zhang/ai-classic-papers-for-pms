# ReAct：ReAct: Synergizing Reasoning and Acting in Language Models

> 分类：推理与 Agent  
> 年份：2022  
> 论文：https://arxiv.org/abs/2210.03629  
> 状态：draft

## 一句话

ReAct 提出了一种让大模型「边想边做」的范式：把「推理」（写出想法、计划）和「行动」（调用工具、搜索、操作环境）交替穿插起来，形成「想一步 → 做一个动作 → 看一眼结果 → 再想 → 再做」的循环；推理帮模型规划和纠偏，行动让它从外部世界拿到真实信息来纠正幻觉——它是今天几乎所有「会用工具的 AI agent」在思想上的共同祖先，而它本身只是一种提示范式，不是某个具体模型。

## 背景问题

CoT（思维链）让模型学会了「先想再答」，但它有一个根本局限：**它是闭卷考试**。

CoT 的推理完全发生在模型「脑子里」——它只能调用预训练时记住的知识，没法在推理过程中查任何外部资料。这带来两个问题：

- **会一本正经地编**。遇到模型不知道、或记错的事实，CoT 不会停下来核查，而是顺着语气把错误信息编进推理链，越推越偏。
- **无法更新**。世界在变（今天的股价、最新的文档、某个 API 的返回），闭卷的 CoT 永远只能用训练时那份过时的记忆。

另一条路线是「只行动的 agent」：让模型去操作环境、调用工具（比如早期让模型操作网页、玩文字游戏的工作）。但纯行动的 agent 又缺了「想」——它能执行动作，却不擅长规划、拆解任务、在出错时调整策略，容易在环境里乱撞、陷入死循环。

于是出现了一个很自然的问题：**人类做复杂任务时，本来就是「想想再做、做完看结果再想」交替进行的——能不能让大模型也这样，把「推理」和「行动」结合起来，让两者互相增益？** ReAct 的名字就是 **Rea**soning + **Act**ing 的合写。

## 核心方法

### 1. 核心循环：Thought → Action → Observation，再回到 Thought

ReAct 的做法是在提示里示范一种交替的格式，让模型按这个循环运转：

- **Thought（想法）**：模型用自然语言写下当前的推理——我现在该干什么、为什么、下一步计划是什么。
- **Action（行动）**：模型输出一个结构化的动作，比如「搜索：xxx」「查询某 API」「在环境里走一步」。这个动作会被外部系统真正执行。
- **Observation（观察）**：外部系统执行动作后，把结果（搜索返回、API 响应、环境反馈）喂回给模型。

然后模型基于这个新的观察，再写下一个 Thought，再发起一个 Action……如此循环，直到它认为可以给出最终答案。

举个例子，回答一个需要查资料的问题：模型先 Thought「我需要先知道 X 是谁」，发起 Action「搜索 X」，拿到 Observation「X 是……」，再 Thought「那我还得查 Y 和 X 的关系」，再 Action……一步步把答案拼出来。

### 2. 两者如何互相增益

ReAct 的精髓在于「想」和「做」的**协同**，而不只是简单叠加：

- **推理让行动更聪明**：Thought 帮模型规划该调用什么工具、按什么顺序、出错了怎么调整。它把一串孤立的动作组织成一个有计划的过程，遇到死胡同能退回来换路。
- **行动让推理更靠谱**：每个 Action 拿回的真实 Observation，给推理注入了**外部世界的事实**。模型不再只靠记忆瞎编，而是用查到的真实信息来支撑下一步推理——这直接压低了 CoT 那种闭卷幻觉。

一句话：CoT 是「只想不做」，纯行动 agent 是「只做不想」，ReAct 是「想和做绑在一起、互相纠偏」。

### 3. 它是一种「范式」，靠提示就能跑起来

要特别强调：ReAct 本质是一种**提示范式 / 交互框架**，不是一个新模型、也不需要专门训练。论文主要是用 few-shot 提示，给模型几个「Thought-Action-Observation」交替的示范，模型就能模仿这个格式去运转。它把「一个语言模型」+「一组可调用的工具/环境」组织成了一个能解决复杂任务的**agent**。

论文在多个任务上验证：需要查 Wikipedia 的多跳问答（HotpotQA）、事实核查（FEVER）、文字版的家务环境（ALFWorld）、模拟网购（WebShop）等。结果是：ReAct 比纯 CoT 更少幻觉、比纯行动 agent 更会规划，两边的好处都占。

### 归因红线

- ReAct 是一种 **agent 范式 / 提示框架**，**不是某个具体模型**。「ReAct」指的是「推理与行动交替」这个方法，不是一个叫 ReAct 的模型。
- 它把「工具调用 / 观察反馈」系统地引入了语言模型的推理循环，但它**靠提示实现**，不涉及训练。今天很多 agent 把工具使用**训练进**了模型（原生 function calling），那是后续发展，ReAct 是思想源头而非那些实现本身。
- 它解决幻觉的方式是**用外部检索/工具来 grounding**，不是从根本上让模型变得更诚实——观察错了、工具返回错了，它照样会被带偏。

## 为什么经典

第一，它给「AI agent」立了一个极其通用、极其简洁的骨架。「Thought → Action → Observation」这个循环，几乎是后来所有 agent 框架（包括各种工具调用、function calling、agent 编排库）的共同模板。今天你听到的「agent loop」「ReAct agent」，思想都在这里。

第二，它把「推理」和「使用外部世界」缝到了一起。在它之前，CoT 把推理关在模型内部；ReAct 第一次清楚地展示，让模型在推理途中去**查、去做、去观察**，能同时提升可靠性和能力。这是从「会说话的模型」走向「会做事的 agent」的关键一步。

第三，它给幻觉问题提供了一条工程上可操作的缓解路径：不是靠把模型训得更诚实，而是靠**让它去检索真实信息再推理**。这条「检索/工具 grounding」的思路，和 RAG 一起成了实用系统对抗幻觉的主力手段。

第四，它的可解释性是「免费」的副产品。因为模型把每一步 Thought 都写出来了，你能清楚看到它「为什么决定查这个、为什么走这一步」，这对调试 agent、向用户解释、做安全审计都很有价值。

## 产品经理启发

1. **「会聊天的模型」和「会做事的 agent」是两种产品，差别就在这个循环。** 如果你的产品需要模型去查实时信息、调用系统、执行多步任务，光有强模型不够，你需要把它放进一个「想—做—看—再想」的循环里，并接上真实的工具和数据。ReAct 是这个循环最朴素的蓝本。

2. **对抗幻觉，最务实的办法常常是「让它去查」而不是「让它更聪明」。** 与其指望模型记得准，不如在它该用事实的地方，强制它先检索/调用工具再回答。产品设计上，识别出「哪些环节必须 grounding 到外部真实数据」，比单纯换更大模型更能解决可靠性问题。

3. **工具和环境的质量，直接决定 agent 的质量。** ReAct 的每个 Observation 来自外部工具，工具返回得准不准、快不快、稳不稳，直接决定 agent 表现。做 agent 产品时，工具/API 的可靠性、错误处理、返回格式，往往比模型本身更值得投入——agent 经常不是「模型不行」，而是「工具不行」。

4. **可观测的推理轨迹是 agent 产品的运营资产。** ReAct 让每一步想法和动作都可见。把这条 Thought-Action-Observation 轨迹记录下来，是你调试失败案例、做质量监控、向用户解释、满足审计要求的基础设施。从第一天就把「轨迹可观测」当成需求，而不是事后补。

5. **多步 agent 的风险是「步步错、错错叠加」。** 循环越长，单步出错被放大、跑偏、陷入死循环的概率越高。产品上要给 agent 设护栏：最大步数、超时、对危险动作的人工确认、检测到打转就中断。别假设「让它一直想下去就会成功」。

6. **「让 agent 自己做」和「成本/延迟/失控风险」要一起算。** 每一步 Thought 和 Action 都是 token 和工具调用，多步循环又慢又贵，还可能执行有副作用的动作。要分清哪些任务值得上完整 agent 循环，哪些用一次性检索（RAG）或固定流程就够了——不是所有任务都该交给一个自由发挥的 agent。

## 局限与争议

第一，它只是提示范式，能力上限受限于底座模型。ReAct 不训练模型，模型本身推理弱、不会规划，套上这个循环也救不回来。它是「组织能力的框架」，不是「制造能力的方法」。

第二，强依赖工具和环境。Observation 来自外部，工具返回错误、超时、格式不一致，都会直接污染推理。一个返回了错误信息的搜索，会让 ReAct 自信地推出错误结论——grounding 到错的东西比不 grounding 更危险。

第三，错误会沿着循环累积。多步任务里，前面一步的小偏差会被后面继承放大，agent 容易越走越偏，或在两三个动作间反复横跳、陷入死循环。步数越长越脆弱。

第四，成本、延迟、稳定性都更差。相比一次问答，ReAct 要多轮生成 + 多次工具调用，又慢又贵，且每多一步就多一个出错点。在高并发、低延迟场景未必划算。

第五，安全面更大。一个能真正「行动」的 agent，可能调用有副作用的工具（发邮件、改数据、下订单）。提示注入、被诱导执行危险动作等风险，比纯问答模型严重得多，需要专门的权限控制和确认机制。

第六，原始 ReAct 靠人工写 few-shot 范例、靠提示拼装。今天的主流已经把工具使用**训练进**模型（原生 function calling、专门的 agent 训练），并有成熟的 agent 框架——这些是后续工作，ReAct 提供的是思想骨架，不是现代 agent 的完整实现。

## 今天怎么看

今天看 ReAct，它的地位是**现代 AI agent 的思想原型**。你现在用到的几乎每一个「会调工具、会查资料、会分步做任务」的 agent，其内核都是那个「Thought → Action → Observation」的循环，只是工程上被打磨、被训练化、被框架化了。

仍然重要的部分：

- 「推理 + 行动交替、互相纠偏」是 agent 的根本范式，没有过时；
- 「用检索/工具 grounding 来压低幻觉」仍是实用系统对抗幻觉的主力思路；
- 「可观测的推理-动作轨迹」是 agent 调试、监控、审计的基础；
- 「多步循环 = 能力更强但更脆弱、更贵、风险更大」这组权衡，是所有 agent 产品的核心取舍。

已经被后续工作改造或扩展的部分：

- 靠 few-shot 提示触发工具使用，被原生 function calling、专门的 agent 训练替代；
- 单纯的 ReAct 循环被加上反思/自我修正（如 Reflexion）、规划、记忆、多 agent 协作等更复杂的结构；
- 工具生态从「手写几个动作」发展到标准化的工具协议、丰富的工具库和编排框架。

对 AI 产品经理来说，ReAct 是从「模型」到「agent」这一步的概念分水岭。它提醒我们：要让 AI 真正「做事」，关键不只是模型多强，而是你怎么把它放进一个能想、能做、能看见结果再调整的循环里，并接好工具、设好护栏、留好轨迹。模型提供智力，agent 架构提供让智力作用于真实世界的通道——而这个通道，既是能力的来源，也是风险和成本的来源。

- ReAct 在推理中穿插 Action 去检索/调用工具，把外部真实信息（Observation）拿回来支撑下一步推理。

2. 描述 ReAct 的「Thought → Action → Observation」循环，并说明推理和行动是怎么互相增益的。

<details>

- Thought：写下当前想法/计划；Action：发起一个被外部执行的动作（搜索/调 API/操作环境）；Observation：把执行结果喂回模型；再回到 Thought，循环到给出答案。
- 推理让行动更聪明：帮规划该用什么工具、什么顺序、出错怎么调整。
- 行动让推理更靠谱：真实 Observation 给推理注入外部事实，减少瞎编。

</details>

<details>
<summary>参考要点（先自己答，再展开）</summary>

- 前提：它解决幻觉靠外部工具/检索 grounding，不是让模型本身更诚实——Observation 的质量决定一切。
- 工具返回错误/超时/格式不一致会直接污染推理，模型会自信地基于错信息推出错结论。

</details>

5. 多步 agent 循环比一次性问答「更强但更脆弱」，体现在哪些方面？产品上该设哪些护栏？

<details>

- 更强：能规划、分步、调用工具完成复杂任务；更脆弱：错误沿循环累积放大，易跑偏或陷入死循环。
- 成本/延迟更高（多轮生成 + 多次工具调用），出错点更多，还可能执行有副作用的动作。

</details>
