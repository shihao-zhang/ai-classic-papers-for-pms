# ZeRO：ZeRO: Memory Optimizations Toward Training Trillion Parameter Models

> 分类：训练基础设施  
> 年份：2019  
> 论文：https://arxiv.org/abs/1910.02054  
> 状态：reviewed

## 一句话

ZeRO 发现：在最常用的数据并行训练里，每张 GPU 都各存一份完整的「模型状态」（参数、梯度、优化器状态）其实是巨大的浪费——它把这些状态**切片分摊**到所有 GPU 上、用到的时候再临时拼回来，从而在几乎不改模型结构、不牺牲数据并行效率的前提下，把单卡显存占用降低一个数量级，让原本塞不进显卡的大模型变得训得动；它是 DeepSpeed 的核心，也是后来 PyTorch FSDP 的思想原型。

## 背景问题

训练越来越大的模型，第一个撞上的墙往往不是算力不够，而是**单张 GPU 的显存装不下**。这堵墙叫「显存墙」。

要理解 ZeRO，先得看清训练时显存到底被谁吃掉了。以混合精度 + Adam 优化器这种主流配置为例，对一个有 Ψ 个参数的模型，每一步训练大致要在显存里同时存着：

- 一份 fp16 的参数（用来前向/反向计算）；
- 一份 fp16 的梯度；
- 一份 fp32 的「优化器状态」——包括 fp32 的参数副本、Adam 的一阶动量、二阶动量。

算下来，优化器状态那部分（fp32 副本 + 两个动量）往往是大头，比参数本身还重好几倍。也就是说，**真正压垮显存的常常不是模型参数，而是为了训练它而附带的那一堆优化器状态。**

而当时最常用的扩展方式——**数据并行（data parallelism）**——在这件事上特别浪费：它让每张 GPU 处理不同的数据批次，但**每张卡都各存一份一模一样的完整模型状态**。你有 1000 张卡，就把同样的优化器状态复制了 1000 份。卡越多，冗余越夸张，但单卡能塞下的模型大小一点没变。

另一条路是改模型结构来分摊——比如张量并行（tensor parallelism，把单个矩阵运算切到多卡）或流水线并行（pipeline parallelism，把不同层放到不同卡）。但这些需要对模型做精细的手术、对代码侵入很深、调起来很费工程。

ZeRO 的问题意识就是：能不能**保留数据并行的简单和高效，同时干掉它「每张卡都存一份完整状态」的冗余**？

## 核心方法

ZeRO 的名字是 **Zero Redundancy Optimizer（零冗余优化器）**，核心动作就一个词：**把复制改成切片（partition / shard）**。

数据并行原本是「每张卡存全量状态」。ZeRO 改成「每张卡只存全量状态的 1/N，需要某一块时再通过通信临时凑齐」。它分三个递进的阶段，切的东西越来越多，省的显存越来越多，代价是通信越来越重。

### 1. ZeRO-1：切分优化器状态（optimizer states）

先拿最大的那块开刀。优化器状态（fp32 副本 + 两个动量）被均匀切成 N 份，每张卡只保管自己负责的那一份。前向、反向照常做，只是在更新参数那一步，每张卡只更新自己那一片，再把更新后的参数同步给大家。因为优化器状态是显存大头，光这一步就能省下相当可观的显存。

### 2. ZeRO-2：再切分梯度（gradients）

在 ZeRO-1 基础上，把梯度也切片。反向传播算出梯度后，每张卡只需保留自己那一片优化器状态对应的梯度，其余可以及时释放。显存进一步下降。

### 3. ZeRO-3：连参数（parameters）也切分

最彻底的一档：连模型参数本身也切片，每张卡平时只持有 1/N 的参数。当某一层要做前向或反向计算时，临时把这一层完整的参数从各卡「拼」回来（all-gather），算完就再释放。这样单卡显存占用几乎和「模型有多大」解耦，理论上卡越多能训的模型越大。

### 一句话抓住它和别的并行的区别

**ZeRO 本质仍然是数据并行**——每张卡处理不同的数据，只是不再各存一份完整状态，而是把状态摊开。它**不是**张量并行，也**不是**流水线并行：那两者是把「单次计算」拆到多卡，ZeRO 是把「存储的状态」拆到多卡。正因为思路正交，ZeRO 可以和张量/流水线并行**叠加**使用（业界俗称 3D 并行），用来训练最大的那批模型。

天下没有免费的显存：省下来的存储是用**通信换的**。切得越细（尤其 ZeRO-3），训练过程中临时拼装参数/梯度的网络流量就越大，对 GPU 之间的互联带宽要求也越高。

## 为什么经典

第一，它**重新定义了大模型训练的显存成本公式**。在 ZeRO 之前，「这个模型能不能训」很大程度由单卡显存决定；ZeRO 之后，显存可以随着卡数近似线性地摊薄，让「加卡」不只是加算力，也是加可用显存。这把一大批原本只有极少数机构能碰的大模型，拉进了更多团队的可行域。

第二，它**用很低的工程代价换来很大的收益**。张量并行、流水线并行都要对模型动刀；ZeRO 基本保持数据并行的编程心智，对上层代码侵入小，因此很容易被集成进框架、被广泛采用。它落地为微软的 **DeepSpeed** 库，又深刻影响了 PyTorch 的 **FSDP（Fully Sharded Data Parallel）**——FSDP 在思想上就对应 ZeRO-3。今天你点开任何一个大模型训练栈，几乎都能看到 ZeRO/FSDP 的影子。

第三，它点明了一个朴素但强大的工程杠杆：**消除冗余**。「每个 worker 都存一份完全一样的东西」是分布式系统里随处可见的浪费，ZeRO 把它系统化地识别、切分、按需重组。这个思路本身具有普适性。

需要划清边界：ZeRO 是**省显存的数据并行**，它分片的是优化器状态、梯度、参数这些**存储**。它**不等于**张量并行或流水线并行本身——后两者解决的是「单次计算太大放不下/算不快」，而 ZeRO 解决的是「状态存储太冗余」。此外，把状态进一步卸载到 CPU 内存甚至 NVMe 硬盘的 ZeRO-Offload、ZeRO-Infinity 是**后续工作（2021 年）**，不应一并算到这篇 2019 原始论文头上；标题里「训练万亿参数模型」也更多是方向性宣示，真正训出超大模型还要叠加更多并行与卸载手段。

## 产品经理启发

1. **大模型训练的第一性约束常是显存，不是算力。** 评估「我们能不能训/微调这个规模的模型」时，PM 的直觉不能只停在「需要多少 FLOPs / 多少卡」，而要问「单卡显存放得下吗、状态怎么摊」。很多「训不动」其实是显存墙，而显存墙是可以用 ZeRO/FSDP 这类技术按卡数摊薄的——这会直接改变项目的可行性判断和预算。

2. **要看清成本到底花在哪：训练时优化器状态比参数更吃显存。** 一个「7B 参数」的模型，真正的显存占用远不止存 7B 个数那么简单，优化器状态可能是参数的好几倍。PM 在和工程团队对账、估算资源时，知道这个结构能避免严重低估成本，也能理解「为什么微调一个看起来不大的模型还是要很多卡」。

3. **省资源的代价通常是通信，互联带宽是隐藏成本项。** ZeRO 切得越细越省显存，但网络流量越大。这意味着同样数量的 GPU，配高速互联（如 NVLink、InfiniBand）和配普通网络，能达到的有效训练规模和速度差别巨大。PM 在做算力采购/云选型时，不能只比 GPU 单价和数量，互联拓扑和带宽是决定能不能高效跑大模型的关键，常被忽略。

4. **优先用成熟的现成杠杆，别重造轮子。** ZeRO 早已封装进 DeepSpeed、PyTorch FSDP 等开源框架。对绝大多数团队，「能训多大模型」更多取决于会不会用好这些现成能力，而不是自研并行策略。PM 做技术规划时应推动团队站在成熟基础设施上，把稀缺工程力投到产品差异化的地方。

5. **「消除冗余」是个可迁移的成本思维。** ZeRO 的内核——发现「大家各存一份完全相同的东西」是浪费，然后切分按需重组——在产品和系统的很多地方都适用：缓存、存储、推理时的 KV、特征复用……看到「重复存储/重复计算」，往往就藏着降本空间。

## 局限与争议

第一，**通信开销是真实代价，慢网络上会反噬。** ZeRO-3 尤其依赖频繁的 all-gather / reduce-scatter，在互联带宽不足的集群上，省下的显存会被拖慢的吞吐吃掉，得不偿失。它的收益高度依赖底层网络条件。

第二，**它只省显存，不省总算力。** ZeRO 不减少需要做的浮点运算总量，模型该算多少还得算多少。它解决「放不下」，不解决「算得慢/算得贵」。

第三，**单靠 ZeRO 训不出最大的模型，需要和其他并行叠加。** 对真正前沿规模的训练，业界普遍是 ZeRO/数据并行 + 张量并行 + 流水线并行的 3D 组合。论文标题的「万亿参数」是方向性愿景，落地仍要大量额外工程，不能误读成「用了 ZeRO 就能轻松训万亿」。

第四，**卸载（offload）类扩展是用别的资源换显存，各有代价，且属于后续工作。** ZeRO-Offload / ZeRO-Infinity 把状态搬到 CPU 内存或 NVMe，能在少卡上训更大模型，但代价是更高的延迟和更复杂的数据搬运，适合特定场景而非银弹；它们也不是 2019 原始 ZeRO 的内容。

## 今天怎么看

今天 ZeRO 已经是大模型训练的「水电煤」级别基础设施。你可能不直接调它的 API，但只要用 DeepSpeed 或 PyTorch FSDP 训练/微调大模型，你就在用 ZeRO 的思想。

仍然重要的部分：

- **「把复制改成切片」的分片数据并行**，是今天训练栈的默认组成之一（ZeRO / FSDP）；
- **显存成本结构的认知**——优化器状态是大头、显存可随卡数摊薄——仍是估算大模型训练资源的基础常识；
- **显存省下来要用通信换**这条权衡，依然决定着集群该怎么配互联、训练能跑多大多快；
- **消除冗余**作为通用工程降本杠杆，长期有效。

已经被扩展或需要叠加的部分：

- 单独的 ZeRO 不足以撑起最前沿规模，需与张量并行、流水线并行组成 3D 并行；
- 卸载到 CPU/NVMe 的能力由后续的 ZeRO-Offload / ZeRO-Infinity 补上，是另一组工作；
- 具体实现层面，FSDP、各类通信优化、更激进的低精度（如 fp8）训练等，都在原始 ZeRO 之上继续演进。

对 AI 产品经理来说，ZeRO 最值得记住的不是它分了几个 stage，而是一组判断习惯：**大模型训练先问显存够不够、再问算力够不够；省显存大概率要拿通信去换；而这类能力多半已被开源框架封装好，团队的竞争力应该用在更上层。** 这几条直接关系到一个 AI 项目的可行性、成本和资源规划。

1. 在标准数据并行里，到底是什么被「重复存储」造成了浪费？ZeRO 用一个什么核心动作消除它？

- 数据并行让每张 GPU 处理不同数据，但每张卡都各存一份完整的模型状态（参数、梯度、优化器状态），卡越多复制越多。
- 这些状态在各卡间完全相同，是纯冗余，单卡能塞下的模型大小并没因为加卡而变大。
- ZeRO 的核心动作：把「复制」改成「切片（partition/shard）」，每卡只存 1/N，用到时再通过通信临时拼回来。

</details>

2. 为什么说「真正压垮显存的常常不是模型参数，而是优化器状态」？这对估算训练成本有什么提醒？

<details>
<summary>参考要点（先自己答，再展开）</summary>

- 混合精度 + Adam 下，除了 fp16 参数和梯度，还要存 fp32 参数副本 + 一阶动量 + 二阶动量，这部分往往比参数本身重好几倍。
- 所以「7B 参数」的真实显存占用远超「存 7B 个数」，优化器状态是大头。
- 提醒：估资源时若只按参数量算会严重低估；也解释了为什么微调一个看起来不大的模型仍需很多卡。

</details>

3. ZeRO 的三个阶段分别切了什么？「省得越多、代价是什么」这条权衡如何体现？

<details>
<summary>参考要点（先自己答，再展开）</summary>

- ZeRO-1 切优化器状态；ZeRO-2 再切梯度；ZeRO-3 连参数也切，用时临时 all-gather 拼回。
- 切得越多，单卡显存占用越低，ZeRO-3 几乎让单卡显存与模型大小解耦。
- 代价是通信越来越重：省下的存储是用网络流量换的，对互联带宽要求越来越高。

</details>

4. 为什么说 ZeRO 不等于张量并行或流水线并行？它们的分工和关系是怎样的？

<details>
<summary>参考要点（先自己答，再展开）</summary>

- ZeRO 本质是数据并行：每卡处理不同数据，分片的是「存储的状态」。
- 张量并行 / 流水线并行是把「单次计算」拆到多卡（拆矩阵运算 / 拆层），解决的是计算放不下、算不快。
- 思路正交，可以叠加使用（3D 并行）来训练最大的模型；不能把 ZeRO 和它们混为一谈。

</details>

5. 如果一个团队有很多 GPU 但互联网络较慢，直接上 ZeRO-3 可能出什么问题？PM 该如何看待这件事？

<details>
<summary>参考要点（先自己答，再展开）</summary>

- ZeRO-3 依赖频繁的 all-gather/reduce-scatter，网络慢时省下的显存会被拖慢的吞吐吃掉，整体得不偿失。
- 说明 ZeRO 的收益高度依赖互联带宽，省显存是用通信换的。
- PM 视角：算力采购不能只比 GPU 单价和数量，互联拓扑/带宽（NVLink、InfiniBand）是能否高效训大模型的隐藏关键成本项。

</details>
