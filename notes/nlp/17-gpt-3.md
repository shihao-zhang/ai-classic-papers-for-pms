# GPT-3：Language Models are Few-Shot Learners

> 分类：自然语言处理  
> 年份：2020  
> 论文：https://arxiv.org/abs/2005.14165  
> 状态：draft

## 一句话

GPT-3 证明了：把自回归语言模型和训练数据规模继续放大到 175B 参数后，模型不再只是“预训练后再微调”的底座，而可以通过自然语言指令和少量示例，在不更新参数的情况下完成很多新任务。

## 背景问题

GPT-3 出现前，主流 NLP 产品路线大多是“预训练模型 + 任务微调”：先用大规模文本训练一个通用模型，再为分类、问答、翻译、摘要等具体任务收集标注数据并微调。

这个路线很有效，但对产品经理有三个现实问题：

1. 每做一个新能力，通常都要定义任务、收集样本、训练或微调、上线评估，周期长。
2. 任务边界被数据集格式锁住，产品需求一变，模型能力就要重新适配。
3. 人类其实经常只靠一句说明和几个例子就能学会新任务，而模型还需要大量标注样本，这说明“泛化能力”仍然不够。

GPT-3 关注的核心问题是：能不能让一个模型在推理时直接从上下文里理解任务，而不是每次都靠参数更新学习任务？

## 核心方法

GPT-3 的方法并不复杂，关键是把一个已经验证有效的方向推到当时非常大的尺度。

它使用 GPT 系列的自回归 Transformer：给定前面的文本，预测下一个 token。训练目标仍然是语言建模，不是专门为每个下游任务训练分类头。它的突破点主要在四件事。

第一，scaling：继续扩大模型、数据和计算量。

论文训练了一组不同规模的 GPT-3 模型，最大版本有 175B 参数，也就是 1750 亿个可学习参数。这里的 175B 不是一个神奇阈值，而是一个工程尺度信号：当参数量、训练数据和计算预算一起放大时，模型在许多任务上的表现会持续改善，尤其是少样本场景。

第二，in-context learning：把“学习任务”的过程放进输入上下文。

传统微调是把训练样本变成模型参数的一部分；in-context learning 则是在 prompt 里放入任务说明和示例，让模型在当前对话上下文中归纳模式。例如：

```text
Translate English to French.
cat -> chat
dog -> chien
book ->
```

模型没有因为这几个例子更新参数，但会根据上下文推断“接下来要做英法翻译”，并输出可能的答案。对产品来说，这意味着“输入设计”开始变成一种能力编排方式。

第三，zero-shot、one-shot、few-shot：用不同程度的上下文信息调用模型。

- zero-shot：只给任务说明，不给示例。例如“把下面这段话总结成三点”。
- one-shot：给一个示例，让模型模仿格式和任务。
- few-shot：给少量示例，帮助模型理解任务边界、输出风格和判断标准。

这三者共同改变了产品原型方式：很多 NLP 能力可以先通过 prompt 验证，而不必一开始就投入标注和训练。

第四，prompting：把需求、约束、示例和输出格式写进自然语言。

GPT-3 让 prompting 从“随手问模型”变成了产品设计的一部分。prompt 不只是问题文本，而是一个轻量任务规格：它规定角色、目标、输入、示例、格式、语气和失败边界。好的 prompt 能让模型更稳定，坏的 prompt 会让模型误解任务、胡编、跑偏或输出不可用格式。

## 为什么经典

GPT-3 经典，不是因为它第一次使用 Transformer，也不是因为它解决了所有 NLP 问题，而是因为它把行业范式从“为每个任务训练模型”推向“用一个通用模型通过上下文适配任务”。

它至少改变了四个判断。

1. 模型能力可以通过规模获得，而不只通过任务专用结构获得。过去常见思路是为不同任务设计不同模型或微调方案；GPT-3 强化了“大模型作为通用接口”的路线。
2. 自然语言本身可以成为产品接口。任务说明、示例和输出格式不再只是给人看的说明书，而是直接影响模型行为的控制面。
3. 产品验证速度大幅变化。PM、研究员和工程师可以先用 prompt 快速测试需求是否“模型可做”，再决定是否需要数据、微调、工具调用或流程约束。
4. 能力涌现成为产品规划必须面对的问题。某些能力会在规模变大后突然变得可用，例如简单推理、类比、格式迁移、多任务泛化。但“看起来涌现”不等于稳定可靠，也不等于可直接承诺给用户。

## 产品经理启发

第一，把模型看成“能力平台”，而不是单点功能。

GPT-3 告诉我们，同一个底座模型可以覆盖写作、改写、分类、问答、翻译、代码样式生成等多种任务。产品经理要学会抽象“用户想完成的认知动作”：提取、变换、生成、判断、规划、解释，而不是一开始就把需求拆成很多孤立模型。

第二，prompt 是产品规格的一部分。

在 GPT-3 之后，需求文档不能只写“模型要会总结”。还要写清楚：输入是什么、输出给谁看、允许多长、是否需要引用来源、遇到不确定信息怎么办、能不能拒答、如何处理格式错误。prompt 是低成本实验入口，但不能替代产品规则。

第三，few-shot 示例是一种“软数据”。

少量示例可以让模型理解风格和边界。对 PM 来说，示例库很重要：它不是训练集，却能影响线上表现。示例要覆盖典型输入、边界输入、反例和期望输出，而不是只放漂亮样例。

第四，scaling 给产品带来能力红利，也带来成本和风险。

更大的模型通常更强，但也更贵、更慢、更难解释。产品设计不能只问“最大模型能不能做”，还要问：这个任务是否需要最大模型？是否可以用小模型、规则、检索、缓存或人工审核解决？用户是否愿意为延迟和成本买单？

第五，能力涌现适合探索，不适合裸奔上线。

当模型突然能做某件事，适合快速做原型；但上线前仍要做任务评测、失败样例分析、置信边界、人工兜底和安全策略。产品承诺应基于稳定评估，而不是基于 demo 惊艳程度。

## 局限与争议

第一，GPT-3 的 few-shot 不是人类意义上的真正学习。

模型没有更新参数，也没有形成持久记忆。它是在上下文里做模式匹配和概率续写。这个能力很有用，但不能简单等同于“理解了任务”或“掌握了知识”。

第二，175B 带来能力，也带来高成本。

大规模训练和推理需要巨大计算资源。它推动了通用大模型路线，也拉高了进入门槛。今天做产品时，不能把“继续变大”当成唯一策略。

第三，训练数据来自大规模互联网语料，带来偏见、污染和版权争议。

论文已经讨论了训练语料可能与评测数据重叠的问题。今天看，这类问题更大：模型可能记住敏感信息、复制训练文本、放大社会偏见，也可能在版权和数据授权上引发争议。

第四，输出流畅不等于事实正确。

GPT-3 擅长生成像人写的文本，但它没有内置事实校验机制，容易产生 hallucination。对搜索、医疗、法律、金融、企业知识库等场景，必须引入检索、引用、审计或人工复核。

第五，prompting 不稳定。

同一个任务换一种说法、换几个示例、换输出顺序，结果可能明显变化。这说明 prompt 是强大的控制方式，但不是严格的软件接口。产品要把 prompt 变化纳入测试，而不是只测理想输入。

## 今天怎么看

今天看，GPT-3 更像是现代大模型产品时代的起点之一。

仍然重要的部分：

- scaling 仍然是大模型能力提升的核心变量之一，但已经和数据质量、后训练、工具使用、推理时计算一起组成更复杂的路线。
- in-context learning 仍然是大模型产品的基础能力。聊天、智能体、知识库问答、代码助手，本质上都在利用上下文注入任务信息。
- zero-shot/few-shot 仍然是快速验证需求的好方法，尤其适合早期探索、低频长尾任务和个性化输出。
- prompting 仍然是 PM 和工程师之间的共同语言，可以把需求转成可测试的模型行为。

已经被后续工作补强或替代的部分：

- 仅靠原始语言建模不够。后来的 instruction tuning、RLHF、偏好优化等方法，让模型更会听指令、更符合人类预期。
- 仅靠 prompt 不够。复杂产品通常还需要 RAG、工具调用、函数调用、工作流编排、权限控制和评测体系。
- 仅看 benchmark 不够。真实产品更关心稳定性、可控性、成本、延迟、安全、可解释和失败后的补救。

对产品经理的现实结论是：GPT-3 证明了“通用模型 + 上下文”可以打开大量新场景，但今天做产品不能停留在 prompt demo。要把模型能力放进完整系统里：数据从哪里来，输出如何校验，失败如何处理，成本如何控制，用户如何建立信任。

## 理解检查

1. 为什么 GPT-3 的 few-shot learning 不等于传统机器学习里的“用少量样本训练一个模型”？
2. 如果一个 GPT-3 demo 在 few-shot prompt 下表现很好，产品上线前还需要补哪些评估和保护措施？
3. 175B 参数在这篇论文里代表什么？它为什么重要，又为什么不能被理解成“参数越多产品越好”？
4. in-context learning 对产品经理写需求、设计示例和定义输出格式有什么影响？
5. “能力涌现”为什么既适合激发产品探索，又不适合作为稳定产品承诺的唯一依据？
