# DiT：Scalable Diffusion Models with Transformers

> 分类：生成模型与扩散  
> 年份：2022  
> 论文：https://arxiv.org/abs/2212.09748  
> 状态：draft

## 一句话

DiT 证明扩散模型的核心去噪骨干不一定必须是 U-Net，也可以换成标准 Transformer：把图像的 latent 切成 patch tokens 去做去噪，质量会随着模型规模和计算量呈现清晰、可预期的 scaling behavior——这把扩散生成接进了“做大就更好”的大模型叙事。

## 背景问题

扩散模型兴起后（DDPM、Latent Diffusion 这条线），U-Net 几乎成了图像去噪生成的默认骨干。U-Net 很适合多尺度图像任务：它的下采样—上采样结构加上 skip connection，天生能同时照顾全局结构和局部细节，对图像这种“多尺度信号”有很强的归纳偏置。

但与此同时，另一条线已经在语言、视觉预训练和多模态上反复验证：Transformer 的真正长处不是某个任务上更强，而是**规模化能力**——参数、数据、算力一起放大时，效果会沿着一条相对平滑、可预测的曲线持续变好（scaling law）。GPT、ViT 都是这条曲线的受益者。

于是一个自然的问题浮出来：扩散模型这个去噪骨干，能不能也吃上 Transformer 的 scaling 红利？如果把图像 latent 切成 patch tokens、用 Transformer 来做 denoiser，会不会像语言模型一样，靠“把模型和算力做大”就能持续提升生成质量？

需要先说清 DiT 的目标边界：它要验证的不是“做一个立刻取代所有 U-Net 的产品模型”，而是一条**架构路线是否成立**——diffusion + Transformer 到底有没有可规模化性。这是一篇架构验证论文，不是一个产品系统说明书。

## 核心方法

DiT 的设计哲学和 ViT 很像：尽量不发明新东西，而是把扩散的去噪任务“翻译”成 Transformer 能直接吃的形式，然后让规模来说话。关键是要分清——**变的只是去噪骨干，扩散的任务定义没变。**

### 1. 站在 latent diffusion 肩膀上：先压缩，再扩散

DiT 不是直接在像素上动手，而是建立在 latent diffusion 之上。它先用一个**预训练好的 autoencoder** 把图像压到低维 latent space，然后只在这个 latent 上训练扩散模型。生成时再用 autoencoder 的解码器把 latent 还原成图像。

用人话讲：与其在几十万像素的大画布上来回涂改，不如先把图像压成一张“信息密度很高的小图”，所有去噪都在这张小图上做，最后再放大还原。

这一步的取舍很关键。好处是 token 数量和计算量大幅下降——Transformer 的注意力成本随 token 数平方增长，如果直接在像素上切 patch，token 会爆炸到根本训不动。代价是：DiT 的生成质量上限被这个 autoencoder 框住了，autoencoder 丢掉的细节，扩散骨干再强也补不回来。所以 DiT 的“可规模化”是**在固定的 latent 接口之上**成立的，不是凭空在像素上成立。

### 2. Patch 化 + 标准 Transformer block：把去噪变成处理 token 序列

拿到 latent 后，DiT 把它切成一个个 patch，每个 patch 投影成一个 token，然后就是一摞标准的 Transformer block 在处理这串 tokens——和 ViT 处理图像、GPT 处理文字几乎是同一套机器。这里没有 U-Net 的下采样—上采样金字塔，也没有 skip connection，就是一个“扁平”的、token 之间全局互相看的序列模型。

类比一下：U-Net 像一个专门为图像设计的、带多尺度流水线的专用车间；DiT 则是把图像拆成一堆零件（token），扔进一个通用的、所有零件互相协商的大会议室。专用车间在中小规模上效率高、先验对；通用会议室的好处是结构简单、容易往大了堆、容易复用整个 Transformer 生态。

取舍在于：放弃 U-Net 自带的图像多尺度先验，意味着 DiT 得用更多算力和数据，从数据里把这些结构重新学回来。这正是它“先验更少、上限更高、但更吃规模”的来源——和 ViT 对 CNN 的关系如出一辙。其中 patch size 是个核心旋钮：patch 越小，token 越多、细节越足、质量越好，但计算成本（GFLOPs）也越高。

### 3. 条件注入：时间步和类别信息怎么喂进去

扩散去噪必须知道两件事：现在是第几步（time step `t`），以及要生成什么（类别 / 条件）。U-Net 通常把这些信息加到各层特征上。DiT 则探索了几种把条件注入 Transformer 的方式，并发现一种基于自适应归一化的注入（用条件去调制每个 block 里 LayerNorm 的缩放与偏移，论文称 adaLN，尤其是它的 zero-init 变体）效果最好。

不必记机制细节，记住产品含义即可：**条件信息不是和图像 token 平起平坐地拼进序列，而是被用来“调制”网络每一层的行为**——告诉每个 block “现在处在哪个去噪阶段、目标是什么”，再让它据此调整。取舍是这一步引入了额外的设计空间和调参，但它正是让“同一个 Transformer 骨干”能干好条件去噪的关键拼图。

### 4. 不变的内核：扩散目标没动，动的是骨干

必须反复强调的一点：DiT 的训练目标仍然是扩散模型那套**逐步去噪**的目标（预测噪声、回归式训练），采样也仍是多步迭代。它没有重新发明扩散，也没有改变“从噪声逐步恢复结构”的范式。

用产品语言说：DDPM/LDM 定义了“逐步去噪”这个任务和它的训练/采样流程，DiT 只是在问一个看似很窄、影响却很大的问题——**执行这个去噪任务的主力网络，能不能从 U-Net 换成更适合规模化的 Transformer？** 论文系统地扫了不同 patch size、深度、宽度和计算量，观察生成质量和算力的关系，结论是：模型越大、算力越多，质量指标越好，且这条改善曲线相当清晰。这就是它最核心的发现——Transformer diffusion backbone 存在类似 scaling law 的行为。

## 为什么经典

DiT 经典，核心是因为它把扩散生成接进了“大模型架构趋势”，并给出了可规模化的证据。

第一，它挑战了 U-Net 在扩散里的默认地位。在 DiT 之前，扩散的去噪骨干几乎等同于 U-Net；DiT 证明，把它换成结构更简单、更通用的 Transformer，不仅可行，还能换来更干净的 scaling 行为。这相当于在生成领域重演了一次 ViT 对 CNN 的故事。

第二，它把“生成质量”和“计算规模”之间的关系显式化、可视化了。这对研究和产品团队都很关键：如果一条路线的扩展曲线清晰，那么“多投算力和参数”就成了一个有可预期回报的工程决策，而不是赌博。

第三，它给出了一个跨模态统一的强信号。一旦去噪也能用 token + Transformer 表示，图像生成就和语言、视觉理解、多模态共享同一套底层语言和工具链，长期更容易统一架构、统一基础设施。

第四，它影响了后续不少图像和视频生成路线的架构选择——patch/token 表示、Transformer-like backbone、diffusion transformer 思想被不同程度地采用。但必须划清边界：DiT 是一个**重要的架构信号和证据**，不能把任何具体生成系统（尤其是后来的大型视频/图像生成产品）的完整能力直接归功于 DiT。那些系统还依赖大量数据、训练策略、条件控制、采样器和工程，DiT 只贡献了“Transformer 去噪骨干可规模化”这一块。

## 产品经理启发

1. **架构趋势会跨领域迁移，选型要看“可扩展潜力”而不只是当下分数。** Transformer 从 NLP 走到视觉理解（ViT），再走到扩散生成（DiT），说明一个底层可规模化架构会不断扩张边界。PM 评估生成方案时，不能只按任务类型对号入座，还要问：这个骨干有没有沿着算力曲线继续变强的潜力？一个今天分数略低、但 scaling 曲线漂亮的路线，长期可能比一个已经触顶的路线更值得押注。

2. **Scaling behavior 是路线判断和排期的硬依据。** 如果一个模型做大之后收益忽高忽低，产品投入的风险就很高——你没法预测下一版花了三倍算力能不能换来确定的提升。反过来，扩展曲线清晰意味着团队能据此规划算力预算、数据采购和版本节奏。DiT 的真正产品价值，正是把“做大有没有用”从玄学变成了可规划的工程问题。

3. **归纳偏置 vs 规模化能力，必须按阶段权衡，别无脑追最大 DiT。** U-Net 自带图像多尺度先验，在中小规模、低预算、数据有限的场景往往更省、更稳、更划算；Transformer 骨干更通用、上限更高，但要用更多数据和算力把先验补回来。小团队或成本敏感场景未必适合追求最大的 DiT——“先验更少、上限更高、但更吃规模”这条账要算清楚再选。

4. **生成产品的竞争不只在 prompt 层，底层 backbone 决定能力天花板。** 用户看到的是提示词和样图，但模型能不能扩到更高分辨率、更长视频、更复杂条件、更大数据，很大程度由 backbone 的可规模化性决定。PM 理解这层差异，才能判断一个供应商的“能力边界”究竟在哪、未来还有没有提升空间，而不是被几张精选样图带偏。

5. **供应商说“更可规模化”时，要追问骨干而不是只看样图。** 当对方宣称模型“更能 scale”，应该追问：去噪骨干是什么、用不用 token/patch 表示、scaling 曲线长什么样、采样要几步、单图成本和延迟多少。这些底层问题决定了这条路线能不能持续变强、能不能在你的成本约束下上线，比样图更能反映真实能力边界。

6. **别把“架构证据”错当成“产品已就绪”。** DiT 证明的是一条路线可规模化，不是一个开箱即用的生产方案。它没有解决采样速度、精细控制、文字渲染、身份一致性、安全合规等问题。PM 在向上汇报或对外沟通时，要清楚区分“某架构被验证可行”和“某产品能力已经达成”，避免把研究信号当成已交付的承诺。

## 局限与争议

第一，DiT 的优势高度依赖规模和算力。在小模型、低预算场景，U-Net 自带的图像先验可能更划算、更稳。不能简单说“Transformer 一定优于 U-Net”——这取决于数据量、算力预算和目标分辨率所处的阶段。

第二，DiT 的“可规模化”是建立在 latent diffusion 之上的，不是凭空在像素上成立。它依赖一个预训练 autoencoder 先压缩图像，生成质量上限被这个 autoencoder 框住。把 DiT 理解成“纯粹的端到端架构胜利”是不准确的，它站在 LDM 的肩膀上——这是原论文的设定，不是后续工作才补上的。

第三，原论文主要在**图像生成**（类别条件的 latent 图像生成）上做验证，并没有覆盖文生图、视频、3D、交互式编辑或实时生成。把 DiT 的结论直接外推到这些场景，是后续工作要做的扩展，而不是 DiT 本身证明过的东西——这条边界要划清。

第四，DiT 并没有解决扩散模型的那些老问题：采样仍是多步、慢且贵，精细控制、文字生成、身份一致性、版权与安全风险依旧存在。这些既不是 DiT 制造的，也不是 DiT 解决的；解决它们靠的是 DDIM/快速采样、guidance、ControlNet、安全层等**别人的后续工作**，不应记在 DiT 账上。

第五，公众很容易把 DiT 和后续某些大型视频生成系统直接绑定。更准确的说法是：DiT 提供了“Transformer diffusion backbone 可规模化”的证据，而那些系统的能力来自数据、规模、工程和大量未公开细节的叠加，不能整体回算给 DiT，DiT 也不是它们的完整技术说明。

第六，DiT 也没有声称在生产中取代 U-Net。直到今天，大量产品仍因为成本、速度、开源生态成熟度和工具链而继续选择 U-Net/LDM 路线。“DiT 证明了可行”和“DiT 已经成为生产默认”是两件事，后者并不成立。

## 今天怎么看

今天看 DiT，重点是理解一个正在发生的迁移：生成模型的基础骨干正从“图像专用的 U-Net”走向“更通用的 token/Transformer 系统”。这和语言模型、多模态模型的趋势是一致的——一旦任务能被表示成 token 序列，Transformer 就有机会接管核心建模。对 PM 来说，DiT 更像一把判断生成模型路线图的尺子，而不是一个直接上线的方案。

仍然重要的部分：

- “把去噪骨干换成 token + Transformer”这条可行且可规模化的路线本身；
- 把“生成质量 vs 计算规模”显式化、可视化，让算力投入变成可规划的工程决策；
- 站在 latent diffusion 之上、用 patch token 处理 latent 的通用接口；
- adaLN 式的条件注入：把时间步/类别当作“调制信号”而非序列里的普通 token；
- “先验更少、上限更高、但更吃规模”这条权衡，以及它和 ViT 对 CNN 的同构关系；
- 它给图像生成与语言/多模态统一架构提供的信号。

已经被后续工作改造或替代、或本就不在 DiT 范围内的部分：

- 多步慢采样仍需 DDIM 等快速采样方法来压缩，这不是 DiT 解决的；
- 精细条件控制、文字渲染、身份一致性靠 guidance、ControlNet 等后续工作补齐；
- 文生图、视频、3D、时空建模等扩展是后续系统的贡献，DiT 只在类别条件图像生成上验证过路线；
- U-Net/LDM 并未过时，在成本、速度、开源生态成熟度上仍是很多产品的现实选择。

读 DiT 的价值，是看懂一次骨干层的范式迁移正在发生：当生成任务被表示成 token 序列，Transformer 就有机会像在语言和视觉理解里那样接管核心建模——但“被验证可规模化”离“在你的成本约束下成为产品默认”，中间还隔着采样速度、控制力、生态和工程的一整段路。

## 理解检查

1. DiT 相比 U-Net diffusion，核心改变在哪里？哪些东西其实没变？

<details>
<summary>参考要点（先自己答，再展开）</summary>

- 变的是去噪骨干：从带多尺度先验的 U-Net 换成扁平的、token 全局互看的标准 Transformer。
- 没变的是扩散任务本身：仍是逐步去噪、预测噪声的回归目标、多步采样。
- 一句话：换的是“执行去噪的网络”，不是“去噪这件事”。

</details>

2. 为什么 DiT 要建立在 latent diffusion 之上、在 latent 上切 patch，而不是直接在像素空间切 patch？

<details>
<summary>参考要点（先自己答，再展开）</summary>

- Transformer 注意力成本随 token 数平方增长，像素上切 patch 会让 token 爆炸到训不动。
- 先用预训练 autoencoder 压到低维 latent，token 数和算力大幅下降，才训得起、扩得动。
- 代价：质量上限被 autoencoder 框住，它丢的细节去噪骨干补不回来——DiT 的 scaling 是在固定 latent 接口之上成立的。

</details>

3. Scaling behavior 对产品路线规划具体有什么意义？为什么 PM 会在意一条“清晰的扩展曲线”？

<details>
<summary>参考要点（先自己答，再展开）</summary>

- 曲线清晰 = “多投算力/参数有可预期回报”，把做大从赌博变成可规划的工程决策。
- 可据此规划算力预算、数据采购和版本节奏，降低投入风险。
- 反例：收益忽高忽低的路线，下一版投三倍算力也说不准能换来多少提升。

</details>

4. 哪些后续生成系统的思想可以说“受 DiT 启发”，但绝不能直接归功于 DiT？为什么这条线要划清？

<details>
<summary>参考要点（先自己答，再展开）</summary>

- 可启发：patch/token 表示、Transformer-like 去噪骨干、diffusion transformer 思路。
- 不能归功：任何具体大型视频/图像生成产品的完整能力——那还依赖数据、规模、控制、采样器、安全层和大量工程。
- DiT 只贡献“Transformer 去噪骨干可规模化”这一块证据，不是某个产品系统的技术说明。

</details>

5. 在低成本、数据有限的产品场景中，为什么 U-Net/LDM 路线仍可能比追求最大 DiT 更合适？

<details>
<summary>参考要点（先自己答，再展开）</summary>

- U-Net 自带图像多尺度先验，在中小规模/低预算下更省样本、更稳、更划算。
- Transformer 骨干先验更少、上限更高，但要用更多数据和算力把结构补回来。
- 还有成本、速度、开源生态成熟度和工具链因素——“可规模化”不等于“在你的约束下更优”。

</details>
